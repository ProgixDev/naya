# Mock data

Accounts, codes, cards, scenarios and photos of the mock world the apps run on, and how to add to it. Source of
truth: `services/demo-api/src/seed.ts` (`SCENARIOS`, `DEMO_ACCOUNTS`, `MOCK_FAMILIES`, `buildSeed`). If this page and
the seed disagree, the seed wins: fix this page. Owner: build owner. Last verified: 2026-10-14 against `seed.ts` on
branch `integration/trial-2026-10-14`. (The file keeps its old name, demo-data.md, so links keep working.)

The backend is a mock: the demo API with seeded mock data, mock providers and bots. Since 14 Oct 2026 the apps and the
admin present it as a real product, with no demo wording ([ADR-0058](../adr/0058-present-the-mock-backed-apps-as-a-real-product.md)):
nothing on screen says « démo » or « simulé », and mock outcomes happen on their own. Tell anyone you hand a build to
that it runs on mock data.

All people, documents, vehicles and events are fictional. Identity documents are « SPÉCIMEN · FICTIF » images in
`services/demo-api/fixtures/`, generated by `services/demo-api/scripts/generate-fixtures.py`.

## Cards and payment outcomes

Payments go through a mock provider that answers on its own; nothing on screen says how a card will behave. The
outcome depends on the last four digits of the provider token (`paymentRef` in `services/demo-api/src/services/rides.ts`):

| Salma's card | Outcome |
|---|---|
| Visa •••• 4242 | Confirmed about 3 s after the ride ends |
| Mastercard •••• 0002 | Declined (« Carte refusée par la banque émettrice. »); the receipt offers another card |
| Visa •••• 3155 | Stays pending until forced: launcher, or `POST /dev/providers/payment/<ref>/confirm` or `/fail` |

Adding a card (`card/new`) accepts any Luhn-valid number with a future expiry; only the last four digits reach the mock
tokeniser, so the same table applies (a card ending 0002 is declined). New cards read « Carte •••• NNNN ».

Other mock provider answers (`providerDelaySeconds` in `services/demo-api/src/main.ts` and `src/embedded.ts`):

| Flow | Answer |
|---|---|
| Driver recharge by card | Confirmed after 3 s; the app shows « Paiement en cours » meanwhile |
| Driver recharge at an agency | Confirmed after 8 s; the app shows the reference to present |
| Driver withdrawal | Confirmed after 8 s; to Amina's « Compte épargne » (Banque Populaire •••• 0000), refused after 5 s |
| Passenger wallet top-up | Confirmed after 3 s (card, mobile wallet) or 8 s (agency) |

Force any pending outcome with `POST /dev/providers/<payment|recharge|withdrawal>/<ref>/confirm` or `/fail`
(refs from `GET /dev/provider-jobs`). The refusal then reads « Refusé par le prestataire de paiement. »

## Naya Famille

Salma's family is seeded in every scenario (`MOCK_FAMILIES`): plan Famille Essentiel, Lina (8, École Agdal),
Amina as dedicated chauffeuse, a weekday trip at 08:00 from Hay Riad to École Agdal, recipients Salma « Mère »
(code `1234`) and Youssef « Père » (code `5678`). The chauffeuse's app never receives these codes; the server checks
them, and 5 wrong codes lock the handover (P1). The `famille` scenario moves Lina's next trip to 10 minutes from now.

Load a scenario:

```bash
pnpm demo:seed                                   # write `default` (stop the API first)
pnpm demo:reset                                  # wipe .data and write `default` (stop the API first)
pnpm --filter @naya/demo-api seed first-ride     # any named scenario
curl -X POST http://localhost:4010/dev/reset -H 'Content-Type: application/json' -d '{"scenario":"first-ride"}'
```

The scenario launcher has no visible entry. In a development build (`__DEV__`), long-press the Naya logo on the
welcome screen for 2 s, or open `naya://dev` (passenger) / `naya-chauffeuse://dev` (driver). It resets scenarios, lists
the accounts, advances the server clock (30 s, 2 min), resolves pending provider jobs and switches the automatic
driver. Release builds (TestFlight) have no launcher: to start over on a phone, delete and reinstall the app.

## Adding mock data

Mock records live in data modules, never inside screens:

| To add | Where | Notes |
|---|---|---|
| A passenger or a driver | `buildSeed` in `services/demo-api/src/seed.ts` (`person(...)`, and `vehicleFor(...)` for her car) | Add her to `DEMO_ACCOUNTS` so the launcher lists her, and to the table above |
| A card or a cash method | `pm(...)` in `buildSeed` | Label it as the card reads (« Visa •••• 1234 »); the token's last 4 digits set the outcome |
| A payout account | `s.payoutAccounts.push(...)` in `buildSeed` | Last 4 digits `0000` make withdrawals fail |
| A Naya Famille family | `MOCK_FAMILIES` in `seed.ts` | Parent and chauffeuse by phone; trips by weekday and Rabat time |
| A place | `PLACES` in `packages/domain/src/geo.ts` | Used by search, saved places, the seed and trips |
| A scenario | `SCENARIOS` in `seed.ts`, then its branch in `buildSeed` | Name it after what it is for |
| Identity documents | `services/demo-api/fixtures/`, via `scripts/generate-fixtures.py` | Keep the « SPÉCIMEN · FICTIF » marking |
| A photo shown in the apps (car wash before/after, Famille proof photos) | `packages/assets/mock/` | Replace a file under the same name; expected files and prompts: [packages/assets/mock/README.md](../../packages/assets/mock/README.md) |

Copy in mock records is user-visible: French, « vous », feminine forms, typographic apostrophes, and no « démo »,
« test » or « simulé ». After a seed change, reset (`pnpm demo:reset` or `POST /dev/reset`): there are no migrations, so
an existing `db.json` or phone keeps its old data until then ([ADR-0029](../adr/0029-demo-store-is-versioned-schemaversion-1-and.md)).
Stores seeded before 14 Oct 2026 still show old labels in their data (plates « DÉMO-00x », « Carte de démonstration »
on past rides, no family for Salma) until they are reset.
